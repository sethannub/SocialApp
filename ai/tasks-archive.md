## Sprint 6 - The preview must split long text the way the server will   [DONE 2026-10-16]
Mode: Debug -> Build. Fixes open item 1.
Why: a 318-character one-paragraph post shows red "318/280" and "Single post" in the composer and
preview, but the server will publish it to X as a 2-part thread. The preview must show what will
actually be posted.
Cause (read, not guessed):
- Server `PostSplitter::chunk()` breaks a paragraph that is over the limit by words
  (`splitParagraph`), and a single over-long word by characters (`hardSplit`). Its own Pest tests
  check this (`PostSplitterTest` "breaks a single over-limit paragraph on word boundaries").
- Client `section-split.ts` `packSections()` only packs whole paragraphs and says so ("we never
  split mid-paragraph"); `platform-preview.ts` and `previewSections()` use it, so an over-limit
  paragraph stays one oversized piece.
- The shared parity fixture `tests/Fixtures/post-splitter-parity.json` has no over-limit
  paragraph case, so nothing caught it.
- The counter's "Single post" comes from the post's saved targets at page load
  (`activeSectionTotal`, `chipFor`), not from the live text.
- Length counting already matches (server X = UTF-16 units = JS `length`).
Files in scope (under `app/`):
- `resources/js/lib/compose/section-split.ts` - new `chunkSegment()`: exact port of
  `PostSplitter::chunk` + `splitParagraph` + `hardSplit`; `previewSections()` uses it.
  `packSections()` stays as it is (the editor's paragraph markers need paragraph boundaries)
- `resources/js/lib/compose/platform-preview.ts` - auto-split path uses `chunkSegment()`
- `resources/js/components/compose/composer.tsx` - counter thread size and the tab chip count from
  the live text (same splitter); counter colour judged per part when it is a thread
- New fixture `tests/Fixtures/post-splitter-overlimit-parity.json`: inputs with expected sections
  **generated by running the PHP splitter**, read by a new Pest test AND a new vitest test, so both
  languages are held to the same answer
Do NOT touch:
- `app/Services/Posts/PostSplitter.php` (the server is right), the editor's paragraph markers
  (`tiptap/section-markers.ts`), the existing parity fixture
Acceptance criteria:
- [x] The 318-char test post previews as a 2-part X thread, parts identical to what the server
      saves (276 + rest), no red count
- [x] Counter says "2-post thread" for it, live as you type
- [x] New fixture cases (single long paragraph, short + long paragraph, a 300-char single word,
      exactly-at-limit, Bluesky limit 300) give identical sections in PHP and TS - tested both sides
- [x] Auto-split OFF still shows one oversized red post (unchanged) - code path untouched, not seen
- [x] LinkedIn still one post (unchanged)
- [x] PHP + JS suites pass; Pint / Larastan / oxlint / oxfmt / tsc clean
- [x] Browser: seen in the composer and in the Publish now window (fake account, nothing published)
Known gap left for later: inside a multi-paragraph post, the editor marker for an over-limit
paragraph will still show that paragraph's own count in red, even though it will be split.

## Sprint 5 - Dubai time on screen (UTC stays in storage)   [DONE 2026-10-16]
Mode: Build. Fixes open item 1. CLAUDE.md standing rule 6: "UTC in storage, Asia/Dubai on
screen. One conversion point. Schedules are entered in Dubai time."
Why: every time on screen reads UTC (draft at ~12:00 Dubai showed "8:00 AM"; the Publish now
window says "(UTC)").
Cause (read, not guessed): screens use the workspace's posting-schedule timezone
(`HandleInertiaRequests` shares `postingSchedule->timezone ?? 'UTC'`). There is no posting
schedule yet, and five places hard-code the `'UTC'` fallback: `HandleInertiaRequests.php:240`,
`NextSlotController.php:43`, `Posts/PostingScheduleController.php:32`,
`Settings/WorkspaceSettingsController.php:34`, and the schedule `firstOrCreate` /
`updateOrCreate` defaults. Storage is already UTC (`config/app.php` 'timezone' => 'UTC').
Files in scope (under `app/`):
- `config/app.php` - new `display_timezone` => env('APP_DISPLAY_TIMEZONE', 'Asia/Dubai'): the
  one place the screen timezone comes from when a workspace hasn't chosen one
- the five fallbacks above -> `config('app.display_timezone')`; a new posting schedule starts in it
- `phpunit.xml` - `APP_DISPLAY_TIMEZONE=UTC` so upstream's existing tests keep their UTC
  expectations; our own test sets Asia/Dubai explicitly
- `resources/js/components/compose/publish-confirm-dialog.tsx` - "Dubai time" label instead of
  the raw "(Asia/Dubai)"
- `.env.example*` - document APP_DISPLAY_TIMEZONE
- New test: `tests/Feature/DisplayTimezoneTest.php`
- Local data: set this workspace's posting timezone to Asia/Dubai through Workspace -> Overview
  (drives Shoutrrr's own screen)
Do NOT touch:
- Storage: `config/app.php` 'timezone' stays UTC; no migration; no change to how times are saved
- The scheduler, the queue-slot maths (`NextSlotResolver`) beyond the fallback value
Acceptance criteria:
- [x] With no posting schedule, the app shares Asia/Dubai as the scheduling timezone - tested
- [x] A workspace that picked another timezone keeps it (the fallback never overrides a choice)
- [x] Times are still stored in UTC: a post scheduled for 14:30 Dubai is saved as 10:30Z - tested
- [x] Browser: post list, time picker, calendar and the Publish now window show Dubai time
- [x] PHP + JS suites pass; Pint / oxlint / oxfmt / tsc clean (explicit exit codes)

Also fixed in Sprint 5 (found while testing): Post::scheduledAt setter stores any incoming time as UTC.
