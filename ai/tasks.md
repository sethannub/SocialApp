## Sprint 6 - The preview must split long text the way the server will   [OPEN]
Mode: Debug -> Build. Fixes open item 1.
Why: a 318-character one-paragraph post shows red "318/280" and "Single post" in the composer and
preview, but the server will publish it to X as a 2-part thread. The preview must show what will
actually be posted.
Cause (read, not guessed):
- Server `PostSplitter::chunk()` breaks a paragraph that is over the limit by words
  (`splitParagraph`), and a single over-long word by characters (`hardSplit`). Its own Pest tests
  check this (`PostSplitterTest` "breaks a single over-limit paragraph on word boundaries").
- Client `section-split.ts` `packSections()` only packs whole paragraphs and says so ("we never
  split mid-paragraph"); `platform-preview.ts` and `previewSections()` use it, so an over-limit
  paragraph stays one oversized piece.
- The shared parity fixture `tests/Fixtures/post-splitter-parity.json` has no over-limit
  paragraph case, so nothing caught it.
- The counter's "Single post" comes from the post's saved targets at page load
  (`activeSectionTotal`, `chipFor`), not from the live text.
- Length counting already matches (server X = UTF-16 units = JS `length`).
Files in scope (under `app/`):
- `resources/js/lib/compose/section-split.ts` - new `chunkSegment()`: exact port of
  `PostSplitter::chunk` + `splitParagraph` + `hardSplit`; `previewSections()` uses it.
  `packSections()` stays as it is (the editor's paragraph markers need paragraph boundaries)
- `resources/js/lib/compose/platform-preview.ts` - auto-split path uses `chunkSegment()`
- `resources/js/components/compose/composer.tsx` - counter thread size and the tab chip count from
  the live text (same splitter); counter colour judged per part when it is a thread
- New fixture `tests/Fixtures/post-splitter-overlimit-parity.json`: inputs with expected sections
  **generated by running the PHP splitter**, read by a new Pest test AND a new vitest test, so both
  languages are held to the same answer
Do NOT touch:
- `app/Services/Posts/PostSplitter.php` (the server is right), the editor's paragraph markers
  (`tiptap/section-markers.ts`), the existing parity fixture
Acceptance criteria:
- [ ] The 318-char test post previews as a 2-part X thread, parts identical to what the server
      saves (276 + rest), no red count
- [ ] Counter says "2-post thread" for it, live as you type
- [ ] New fixture cases (single long paragraph, short + long paragraph, a 300-char single word,
      exactly-at-limit, Bluesky limit 300) give identical sections in PHP and TS - tested both sides
- [ ] Auto-split OFF still shows one oversized red post (unchanged)
- [ ] LinkedIn still one post (unchanged)
- [ ] PHP + JS suites pass; Pint / Larastan / oxlint / oxfmt / tsc clean
- [ ] Browser: seen in the composer and in the Publish now window (fake account, nothing published)
Known gap left for later: inside a multi-paragraph post, the editor marker for an over-limit
paragraph will still show that paragraph's own count in red, even though it will be split.

Open items, most severe first.

1. **X preview disagrees with what will be posted** (found in Sprint 4, upstream). A 318-char
   post shows "Single post 318/280" in red in the composer and the preview, but the saved X
   target has auto_split=true with 2 sections and the server precheck finds no problem, so it
   would go out as a 2-part thread. The Publish now window correctly says Ready, next to a red
   preview - confusing. Find which one is right before connecting a real X account.
2. **Needs-reconnect accounts are still attempted** when publishing to the ready ones (Sprint 4).
   The server precheck doesn't know about expired logins, so the dispatcher sends a job with a dead
   token; it fails as an auth error (Failed / needs attention). Same visible result as "skipped",
   but one doomed API call. `[Likely]` from reading `PublishDispatcher`, not seen.
3. **Bluesky and Discord can be connected with no app keys** (app password / webhook). We don't
   use them; hide or disable them so nothing gets connected by accident.
4. **Server checklist (before EZEOS), not code:**
   - Docker publishes on all interfaces by default (`0.0.0.0`). Locally worked around with
     `APP_PORT=127.0.0.1:8095`. On EZEOS: bind to 127.0.0.1, reach it only via the tunnel.
   - Use the production compose file / `APP_ENV=production`, `APP_DEBUG=false`. With
     `APP_ENV=local` the login page pre-fills `test@example.com` / `password` and debug pages
     show internals (`FortifyServiceProvider::defaultLoginCredentials()`, read 2026-10-16).
   - `SESSION_SECURE_COOKIE=true`, `TRUSTED_PROXIES` set for the tunnel (Shoutrrr README).
   - `APP_NAME="Y5Media Social"` (session cookie and cache prefix derive from it).
5. Minor, found in Sprint 2: `FortifyServiceProvider` passes the raw `?invitation=` query value
   to `registrationsAllowed(?string)`. A crafted `?invitation[]=x` is an array and would likely

6. Small, from Sprint 3: login page keeps Shoutrrr's centred layout (the branding mockup showed a
   split forest panel) and still says "Registration is disabled for this instance." (mockup:
   "New accounts by invitation only."). Ask the user whether either matters.

   `application/json` but gets `application/json;charset=utf-8` in the bun 1.4.3 container (also
